Encapsulation in Python: The Real Story

Learn how Python communicates public and internal interfaces, what name mangling actually does, and how objects protect valid state.

August 31, 2026 • Ahamed Learning Notes

Encapsulation is a core object-oriented design idea, but Python does not express it with the strict access modifiers found in languages such as Java or C++. Python relies more heavily on interfaces, naming conventions, and cooperation between developers.

01 — The principle

What encapsulation really means

Encapsulation bundles related data and behavior inside an object and exposes a deliberate interface for working with that state. Its purpose is not merely to hide variables.

Good encapsulation helps you:

  • protect an object's valid state
  • prevent accidental misuse
  • define a small, understandable public interface
  • change internal implementation without breaking callers
Core idea: Callers should depend on what an object promises to do, not on every detail of how it does it.

02 — Python's approach

Convention instead of strict access control

Python has no Java-style public, protected, or private keywords for normal attributes. Most state remains technically accessible.

Instead, attribute names communicate how callers are expected to use them:

Form Common description Actual behavior
name Public Part of the normal external interface
_name Protected or non-public Convention: internal use, but still accessible
__name Private Name-mangled to reduce accidental subclass collisions

The words “protected” and “private” are convenient shorthand, but they do not represent enforced visibility levels in Python.

03 — Public attributes

No leading underscore

A public attribute has no leading underscore and is intended for ordinary use by callers. 

class Person:
    def __init__(self, name):
        self.name = name


person = Person("Alice")
print(person.name)  # Alice

person.name = "Sara"
print(person.name)  # Sara

Direct reading and assignment are part of this class's public interface. Public attributes are often perfectly appropriate when no validation or additional behavior is required.

04 — Non-public attributes

A single leading underscore

A single leading underscore signals that an attribute is an internal implementation detail. 

class Person:
    def __init__(self, name):
        self._name = name


person = Person("Alice")
print(person._name)  # Alice

The access works because Python does not block it. The underscore asks callers not to depend on this name unless they have a good reason and accept that it may change.

This convention also affects wildcard imports: a name beginning with one underscore is normally excluded from from module import * unless the module explicitly includes it in __all__.

A single underscore communicates intent to people and tools. It is not an access-control barrier.

05 — Name mangling

A double leading underscore

A name beginning with two underscores and not ending with two underscores triggers name mangling inside a class definition. 

class Person:
    def __init__(self, name):
        self.__name = name


person = Person("Alice")
print(person.__dict__)
{'_Person__name': 'Alice'}

Python rewrites __name using the class name. Therefore, this direct access fails: 

print(person.__name)
# AttributeError: 'Person' object has no attribute '__name'

The mangled name remains accessible:

print(person._Person__name)  # Alice
Name mangling is not secrecy or security. It makes accidental name collisions less likely, especially in subclasses.

06 — Inheritance safety

Why name mangling matters in subclasses

class A:
    def __init__(self):
        self.__value = 10

    def value_from_a(self):
        return self.__value


class B(A):
    def __init__(self):
        super().__init__()
        self.__value = 20

    def value_from_b(self):
        return self.__value


item = B()

print(item.__dict__)
print(item.value_from_a())
print(item.value_from_b())
{'_A__value': 10, '_B__value': 20}
10
20

Code written inside A transforms self.__value into self._A__value. Code inside B transforms the same spelling into self._B__value. The two attributes do not collide.

Without name mangling

class A:
    def __init__(self):
        self._value = 10


class B(A):
    def __init__(self):
        super().__init__()
        self._value = 20


item = B()
print(item._value)  # 20
print(item.__dict__) # {'_value': 20}

Both assignments use the same attribute. The subclass replaces the value initialized by the parent. That may be intentional, but it can also break a base class that expects its internal name to remain under its control.

Name mangling is primarily useful for:

  • avoiding accidental subclass overrides
  • protecting a base class's internal implementation namespace
  • reducing collisions in inheritance hierarchies

07 — Controlled access

Use properties to protect valid state

Naming conventions communicate intent. A property goes further by defining behavior for reading or assigning an attribute while keeping a natural public interface. 

class BankAccount:
    def __init__(self, balance=0):
        self._balance = balance

    @property
    def balance(self):
        return self._balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("deposit must be positive")

        self._balance += amount

    def withdraw(self, amount):
        if amount <= 0:
            raise ValueError("withdrawal must be positive")

        if amount > self._balance:
            raise ValueError("insufficient funds")

        self._balance -= amount


account = BankAccount(100)
account.deposit(50)
account.withdraw(30)

print(account.balance)  # 120

Callers can inspect balance but must use methods that enforce the account's rules to change it. The important protection comes from the designed interface, not merely from the underscore.

Encapsulation is strongest when behavior preserves invariants. An underscore alone cannot keep an object valid.

08 — Practical choices

Which naming style should you use?

  • Use name when callers are expected to depend on the attribute.
  • Use _name for an implementation detail that callers should generally leave alone.
  • Use __name when avoiding accidental subclass name collisions is genuinely valuable.
  • Use a property or method when access needs validation, computation, or other behavior.

Do not add getters and setters automatically to every attribute. Python allows simple public attributes, and you can later replace one with a property without changing the caller's attribute syntax.

09 — Summary

The real story

  • Python does not enforce traditional visibility modifiers.
  • A public name forms part of the supported interface.
  • A single underscore marks a name as non-public by convention.
  • A double underscore triggers class-based name mangling.
  • Name mangling prevents collisions, not determined access.
  • Properties and methods can enforce rules around object state.
Final idea: Encapsulation is the design of a clear interface that keeps an object valid while allowing its internal implementation to evolve.
