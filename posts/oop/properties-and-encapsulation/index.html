Object-Oriented Programming

Properties and Encapsulation in Python

Keep natural attribute syntax while controlling how object state is read, validated, and modified.

September 1, 2026 • Ahamed Learning Notes

Encapsulation becomes practical when an object can protect its own valid state. Python's @property decorator lets a class run logic during attribute access without forcing callers to use awkward getter and setter syntax.

01 — The problem

Uncontrolled attribute access

class Smartphone:
    def __init__(self, brand, operating_system):
        self.brand = brand
        self.operating_system = operating_system


iphone = Smartphone("Apple", "iOS 17")

The object can be changed to a state that makes no sense for the class: 

iphone.operating_system = "Android"
print(iphone.operating_system)  # Android

A public attribute is appropriate when unrestricted assignment is acceptable. When the class has rules to preserve, it needs a controlled interface for changing that state.

Encapsulation is not about hiding everything. It is about deciding which changes are valid and making those rules part of the class.

02 — Signaling intent

Public, non-public, and name-mangled attributes

Python uses naming conventions rather than strict access modifiers.

Name Meaning Enforced?
height Public interface No restriction
_height Non-public implementation detail Convention only
__height Name-mangled within its class Reduces accidental access and subclass collision

A single underscore asks callers not to depend on an internal attribute. A double underscore triggers name mangling, but the value is still technically accessible through its mangled name. Neither form validates new values by itself. 

class Tree:
    def __init__(self, height):
        self._height = height


pine = Tree(20)
pine._height = "Grandma"  # Still allowed by Python

To enforce a rule, the class needs behavior—not only a naming convention.

03 — Traditional control

Getter and setter methods

One approach is to make the internal value non-public and expose explicit methods for reading and updating it. 

class Tree:
    def __init__(self, height):
        self.set_height(height)

    def get_height(self):
        return self._height

    def set_height(self, new_height):
        if isinstance(new_height, bool) or not isinstance(new_height, int):
            raise TypeError("height must be an integer")

        if not 0 < new_height <= 40:
            raise ValueError("height must be between 1 and 40")

        self._height = new_height

The constructor calls the setter so the initial value follows the same rules as every later value. 

pine = Tree(20)
pine.set_height(25)

print(pine.get_height())  # 25

This works, but manipulating the value feels heavier than normal Python attribute access: 

pine.set_height(pine.get_height() + 5)

04 — Property getter

Access behavior with attribute syntax

The @property decorator turns a method into a managed attribute. Callers use attribute syntax, while the class still runs a function. 

class Tree:
    def __init__(self, height):
        self._height = height

    @property
    def height(self):
        return self._height


pine = Tree(17)
print(pine.height)  # 17

The caller writes pine.height, not pine.height(). Behind that expression, the property getter returns pine._height.

A getter-only property is read-only

pine.height = 25
# AttributeError: property 'height' of 'Tree' object has no setter

The public name cannot be assigned until the property defines a setter. This is useful for values callers should inspect but not replace directly.

05 — Property setter

Validate assignment automatically

class Tree:
    def __init__(self, height):
        self.height = height

    @property
    def height(self):
        return self._height

    @height.setter
    def height(self, new_height):
        if isinstance(new_height, bool) or not isinstance(new_height, int):
            raise TypeError("height must be an integer")

        if not 0 < new_height <= 40:
            raise ValueError("height must be between 1 and 40")

        self._height = new_height

The public property is height. The actual value is stored under _height. Using different names prevents the setter from assigning to itself recursively. 

pine = Tree(10)
pine.height = 33

print(pine.height)  # 33

Invalid values are rejected consistently:

Tree("tall")   # TypeError
Tree(100)      # ValueError

pine.height = -5  # ValueError
Assigning self.height = height in __init__ deliberately invokes the property setter. Construction cannot bypass the validation.

06 — Under the hood

A property is a data descriptor

A property is stored on the class and participates in attribute lookup through the descriptor protocol. 

print(Tree.__dict__["height"])
# <property object at 0x...>

Because a property is a data descriptor, it takes priority over an instance dictionary entry with the same public name. Reads and assignments are routed through its getter and setter.

The backing attribute uses another name—here, _height—so the property can store the actual state without triggering itself again.

07 — Computed values

A property does not need stored data

Properties can compute a value from other state instead of exposing a stored attribute. 

class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height

    @property
    def area(self):
        return self.width * self.height


rectangle = Rectangle(4, 6)

print(rectangle.area)  # 24

rectangle.width = 10
print(rectangle.area)  # 60

There is no stored area value to become stale. Each access calculates it from the current dimensions.

08 — API evolution

Add control without changing caller syntax

A class can begin with a simple public attribute: 

class Product:
    def __init__(self, price):
        self.price = price

If validation becomes necessary later, the class can replace that attribute with a property while callers continue using product.price and product.price = value.

You do not need getters and setters for every attribute from day one. Start simple and introduce a property when access needs behavior.

09 — Put it together

Complete example

class Tree:
    def __init__(self, species, height):
        self.species = species
        self.height = height

    @property
    def height(self):
        return self._height

    @height.setter
    def height(self, new_height):
        if isinstance(new_height, bool) or not isinstance(new_height, int):
            raise TypeError("height must be an integer")

        if not 0 < new_height <= 40:
            raise ValueError("height must be between 1 and 40")

        self._height = new_height

    @property
    def description(self):
        return f"{self.species}: {self.height} meters"


pine = Tree("Pine", 20)
print(pine.description)

pine.height = 25
print(pine.description)
Pine: 20 meters
Pine: 25 meters

10 — Summary

Key takeaways

  • Public attributes are appropriate when unrestricted access is safe.
  • Underscores communicate internal intent but do not enforce validation.
  • A getter-only property creates a read-only public attribute.
  • A property setter validates normal assignment syntax.
  • Constructor values should follow the same validation path.
  • Properties can also expose computed values.
Final idea: A property preserves clean attribute syntax while giving the class control over how its state is read and changed.
