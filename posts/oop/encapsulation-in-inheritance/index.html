Encapsulation in Python Inheritance

Decide what child classes should depend on, what remains an implementation detail, and how properties preserve control across a hierarchy.

August 30, 2026 • Ahamed Learning Notes

Inheritance raises an important design question: which parts of a parent class form a supported interface for subclasses, and which parts should remain under the parent's control?

Python does not enforce traditional protected or private access. Instead, naming conventions and name mangling communicate intent, while methods and properties provide controlled interfaces.

01 — The basic rule

Read names as API signals

Name Meaning for a child class Python behavior
x Supported public interface Normally accessible
_x Subclass-accessible implementation detail Accessible by convention
__x Owned by the defining class Name-mangled using that class name
Public names are promises. Single-underscore names are internal hooks or details. Double-underscore names reduce accidental collisions; they do not create security.

02 — Public interface

Child classes can depend on public members

class Parent:
    def __init__(self):
        self.value = 10


class Child(Parent):
    def show(self):
        return self.value

    def double(self):
        self.value *= 2


child = Child()
print(child.show())  # 10

child.double()
print(child.show())  # 20

The public attribute is part of the parent's supported interface. A child can read it, assign it, and build behavior around it—while still respecting any documented rules.

03 — Internal interface

A single underscore means “use carefully”

class Parent:
    def __init__(self):
        self._value = 10


class Child(Parent):
    def change(self):
        self._value = 50


child = Child()
child.change()
print(child._value)  # 50

Python permits the access. The underscore says the name is not part of the broad public API and may depend on internal assumptions.

A subclass might reasonably use a non-public member when:

  • the parent documents it as a subclass extension point
  • the child is carefully extending internal behavior
  • the project controls both classes and can evolve them together

A child should avoid:

  • bypassing parent validation
  • changing state the parent expects to manage
  • depending on undocumented storage layout without need
Accessibility is not the same as stability. A subclass can access _value, but the parent is not promising every caller that this internal name will remain unchanged forever.

04 — Class-owned names

Double underscores trigger name mangling

class Parent:
    def __init__(self):
        self.__value = 10


class Child(Parent):
    def show(self):
        return self.__value


child = Child()
child.show()
# AttributeError: 'Child' object has no attribute '_Child__value'

Inside Parent, Python rewrites self.__value to self._Parent__value. Inside Child, the same spelling would become self._Child__value. The child is therefore asking for a different name.

The parent value remains technically reachable through the mangled spelling, but depending on that spelling defeats the purpose of keeping the name owned by the parent. 

print(child._Parent__value)  # 10
Double underscores do not make data inaccessible. They protect a class namespace from accidental reuse by subclasses.

05 — Separate storage

The same double-underscore name can coexist

class Parent:
    def __init__(self):
        self.__value = 10

    def parent_value(self):
        return self.__value


class Child(Parent):
    def __init__(self):
        super().__init__()
        self.__value = 50

    def child_value(self):
        return self.__value


child = Child()

print(child.__dict__)
print(child.parent_value())
print(child.child_value())
{'_Parent__value': 10, '_Child__value': 50}
10
50

The parent and child each own a separate attribute. Neither assignment overwrites the other.

This collision avoidance—not strict privacy—is the primary reason to use name mangling in inheritance-heavy designs.

06 — Public behavior

Use methods instead of reaching into storage

class Parent:
    def __init__(self):
        self.__balance = 100

    def get_balance(self):
        return self.__balance


class Child(Parent):
    def show_balance(self):
        return self.get_balance()


child = Child()
print(child.show_balance())  # 100

The child uses a public method rather than depending on the parent's storage name. The parent can later compute the balance, fetch it elsewhere, or change its internal representation without forcing the child to change.

A public interface creates freedom on both sides: the child gets a stable operation, and the parent can evolve its implementation.

07 — Methods

Methods follow the same naming conventions

class Parent:
    def public_method(self):
        return 1

    def _internal_method(self):
        return 2

    def __class_owned_method(self):
        return 3


class Child(Parent):
    def test(self):
        return (
            self.public_method(),
            self._internal_method(),
        )


print(Child().test())  # (1, 2)

The public method is a supported dependency. The single-underscore method is callable but internal. The double-underscore method is mangled as _Parent__class_owned_method, so a method spelled __class_owned_method in Child would be separate rather than an override.

08 — Controlled attributes

A property separates interface from storage

class Parent:
    def __init__(self):
        self.__value = 10

    @property
    def value(self):
        return self.__value

    @value.setter
    def value(self, new_value):
        if new_value < 0:
            raise ValueError("value cannot be negative")

        self.__value = new_value


parent = Parent()
parent.value = 20
print(parent.value)  # 20

The public name is value. The name-mangled __value is only the current storage detail. Callers use normal attribute syntax while the class keeps validation under its control.

09 — Property inheritance

A child can use the inherited property

class Child(Parent):
    def show(self):
        return self.value

    def increase(self, amount):
        self.value += amount


child = Child()
child.increase(5)

print(child.show())  # 15

The child never touches Parent's private storage. Reads go through the inherited getter and updates go through the inherited setter, including its validation.

10 — Getter specialization

A child can specialize a property getter

class DoubledChild(Parent):
    @Parent.value.getter
    def value(self):
        return super().value * 2


child = DoubledChild()

print(child.value)  # 20

child.value = 7
print(child.value)  # 14

The @Parent.value.getter decorator creates a new property with the specialized getter while preserving the parent property's setter and deleter. The getter uses super().value to retrieve the parent-managed value.

Writing only @property in the child would create a new getter-only property and discard the inherited setter. Reusing the parent property's getter decorator preserves it.

11 — Setter specialization

A child can extend assignment rules

class LimitedChild(Parent):
    @Parent.value.setter
    def value(self, new_value):
        if new_value > 100:
            raise ValueError("child value cannot exceed 100")

        Parent.value.__set__(self, new_value)


child = LimitedChild()
child.value = 80
print(child.value)  # 80

child.value = 120
# ValueError: child value cannot exceed 100

The child's setter enforces its extra maximum, then delegates to the parent property descriptor. The parent setter still enforces its non-negative rule and updates the parent's name-mangled storage.

Property setter overriding is an advanced technique. When the validation logic is meant to be extended frequently, a documented protected validation method may produce a simpler subclass API.

12 — Designed extension

Expose a deliberate subclass hook

class Parent:
    def __init__(self, value):
        self.value = value

    def _validate_value(self, value):
        if value < 0:
            raise ValueError("value cannot be negative")

    @property
    def value(self):
        return self.__value

    @value.setter
    def value(self, new_value):
        self._validate_value(new_value)
        self.__value = new_value


class LimitedChild(Parent):
    def _validate_value(self, value):
        super()._validate_value(value)

        if value > 100:
            raise ValueError("value cannot exceed 100")

Here, _validate_value is intentionally designed as a subclass extension point. The property remains the public interface, and the parent remains responsible for storage.

A documented protected hook is often better than asking subclasses to replace an entire property or depend on private storage.

13 — Summary

The inheritance encapsulation model

  • x is the supported public interface.
  • _x is internal but may serve as a subclass hook.
  • __x belongs to the defining class through name mangling.
  • Child classes should prefer interfaces over parent storage.
  • Inherited properties preserve validation and hide representation.
  • Documented protected methods can provide clean extension points.
Final idea: Clean inheritance is less about what a child can technically access and more about which dependencies the parent deliberately promises to support.
